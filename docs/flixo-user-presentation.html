ภาพรวม

เส้นทางที่เราจะพาดูวันนี้

หน้าแรก→ สินค้า→ สมัคร/ล็อกอิน→ ลงขาย→ ชำระเงิน
ออเดอร์→ แชท+ตรวจข้อความ→ รีวิว→ ถอนเงิน→ ข้อพิพาท
แต่ละหน้าจะมีทั้งคำอธิบาย + หลักการทำงาน + หน้าจอจริงด้านขวา

หน้า 1

หน้าแรก (Landing)

สิ่งที่เห็น

  • จุดขายระบบพักเงินกลาง
  • ใช้งาน 3 ขั้นตอน
  • กฎเหล็กความปลอดภัย
  • รายการสินค้า + ค้นหา/กรอง

หลักการทำงาน

  1. เปิดเว็บได้โดยไม่ต้องล็อกอิน
  2. ดึงสินค้าที่เปิดขายจากฐานข้อมูล
  3. ค้นหา/กรอง แล้วแสดงทีละหน้า
ทำไมไม่บังคับล็อกอินก่อน?
ให้ดูของได้เหมือนเดินตลาดจริง สมัครตอนพร้อมซื้อ

หน้า 2

รายละเอียดสินค้า

สิ่งที่เห็น

  • รูป / ราคา / รายละเอียด
  • คะแนนและความน่าเชื่อถือผู้ขาย
  • ปุ่มซื้อ และปุ่มแชท

เมื่อกดซื้อ

  1. ตรวจว่าล็อกอินแล้วหรือยัง
  2. กันซื้อสินค้าของตัวเอง
  3. สร้าง Order (ออ-เดอร์) สถานะรอชำระเงิน
  4. แจ้งเตือนผู้ขาย แล้วไปหน้าชำระเงิน
ตอนกดซื้อมีเงินเข้าเลยไหม?
ยังไม่มี — ตอนนี้แค่จองดีล

หน้า 3

สมัครสมาชิก

หลักการทำงาน

  1. ตรวจข้อมูลและกันอีเมลซ้ำ
  2. เข้ารหัสรหัสผ่านก่อนบันทึก
  3. บันทึกการยินยอมแยกไว้
  4. พาเข้าสู่ระบบ
เข้ารหัสรหัสผ่านหมายความว่าอะไร?
ไม่เก็บรหัสจริงในฐานข้อมูล เก็บเป็นค่าที่แปลงแล้ว ตอนล็อกอินค่อยเทียบ
ทำไมต้องติ๊กยอมรับ?
มีหลักฐานยินยอมก่อนใช้งาน ตามหลักคุ้มครองข้อมูลส่วนบุคคล

หน้า 4

เข้าสู่ระบบ

  1. รับชื่อผู้ใช้/อีเมล + รหัสผ่าน
  2. ค้นหาบัญชีจากฐานข้อมูล
  3. ตรวจสถานะบัญชีก่อนเทียบรหัสผ่าน
  4. เทียบรหัสผ่านกับค่าที่เข้ารหัสไว้
  5. สร้าง Session (เซส-ชั่น) ใหม่
Session คืออะไร?
บัตรผ่านชั่วคราวหลังล็อกอิน ใช้บอกระบบว่าใครกำลังใช้งาน

ทิป: ล็อกอินในแท็บนี้ก่อน แล้วสไลด์หน้าหลัก/ลงขาย/ออเดอร์จะโชว์หน้าจริงได้เมื่อกด “หน้าจริง”

หน้า 4 — ตรวจสถานะบัญชี

“ตรวจว่าบัญชีไม่ถูกระงับ” ทำยังไง?

ทุกบัญชีมีฟิลด์สถานะในฐานข้อมูล เช่น active / banned

  1. หาบัญชีจากชื่อผู้ใช้หรืออีเมลที่กรอก
  2. อ่านค่า status ของบัญชีนั้น
  3. ถ้าเป็น banned → ปฏิเสธทันที แจ้งว่าบัญชีถูกระงับ
  4. ถ้าไม่ใช่ active → ปฏิเสธเช่นกัน (บัญชียังใช้ไม่ได้)
  5. ผ่านแล้วค่อยเทียบรหัสผ่าน — กันไม่ให้บัญชีถูกระงับยังล็อกอินได้
ทำไมต้องเช็กสถานะก่อนเทียบรหัสผ่าน?
แม้รหัสถูกก็ไม่ควรเข้าได้ ถ้าถูกระงับเพราะโกง/ผิดกฎ — สถานะบัญชีมาก่อนสิทธิ์เข้าใช้
หลักการ: สิทธิ์เข้าใช้ระบบขึ้นกับสถานะบัญชี ไม่ใช่แค่รู้รหัสผ่าน

หน้า 6

ลงประกาศขาย

หน้านี้คือฟอร์มลงขายจริง — กรอกรูป ชื่อ ราคา รายละเอียด

ภาพรวม pipeline

  1. รับรูปและข้อมูลสินค้า
  2. ชั้น 1: ตรวจข้อมูลต้นทางรูปแบบเร็ว (ไม่เสียค่า API)
  3. ถ้าน่าสงสัย → ชั้น 2: ส่ง Google Cloud Vision (กู-เกิล คลาวด์ วิ-ชั่น)
  4. ไม่ผ่าน → ไม่บันทึกสินค้า
  5. ผ่าน → เปิดประกาศในตลาด
ทำไมตรวจก่อนบันทึก?
ไม่ให้ของเสี่ยงหลุดขึ้นตลาดก่อน แล้วค่อยมาลบทีหลัง

หน้า 6 — ชั้นที่ 1

“ตรวจรูปเบื้องต้นแบบเร็ว” ใช้อะไร?

ใช้ข้อมูล EXIF (อี-ซิฟ) ในไฟล์รูป + ขนาดไฟล์ ไม่ได้อ่านเนื้อหารูปด้วย AI ตอนนี้

EXIF คืออะไร

ข้อมูลแอบอยู่ในไฟล์รูป เช่น ยี่ห้อกล้อง รุ่น วันถ่าย พิกัด GPS

ทำไมใช้ตรวจ

รูปถ่ายจากมือถือจริงมักมีข้อมูลกล้อง รูปก็อปจากแชท/เว็บมักไม่มี

ระบบให้คะแนนความน่าเชื่อถือของรูป

  • มียี่ห้อกล้อง → เพิ่มคะแนน
  • มีรุ่นกล้อง → เพิ่มคะแนน
  • มีวันเวลาถ่าย → เพิ่มคะแนน
  • มี GPS → เพิ่มคะแนน
  • พบว่าผ่านแอปแชท/แต่งรูป (Line, Canva ฯลฯ) → ลดคะแนน
  • ไฟล์เล็กมาก + ไม่มีข้อมูลกล้อง → ลดคะแนน

หน้า 6 — เมื่อไหร่ถึง “น่าสงสัย”

ถ้าน่าสงสัย เป็นเพราะอะไร?

ถ้ารวมคะแนนความน่าเชื่อถือของรูป ต่ำกว่าเกณฑ์ประมาณ 65 ระบบจะถือว่าน่าสงสัย

เคสพบบ่อย

ไม่มี EXIF เลย — มักเป็นรูปก็อปจากแชทหรือเว็บ

เคสไฟล์เล็ก

ถูกบีบอัดจากแชท แล้วไม่มีข้อมูลกล้อง

เคสผ่านแอป

metadata บอกว่าผ่าน Line / Facebook / Canva

น่าสงสัยแล้วทำอะไรต่อ?
ยังไม่บล็อกทันที — ส่งต่อไปให้ Google Cloud Vision ช่วยดูเนื้อหารูปต่อ
ชั้น 1 = กรองหยาบฟรี · ของที่ดูน่าเชื่อถือผ่านเลย · ของน่าสงสัยค่อยเสียค่า AI

หน้า 6 — ชั้นที่ 2

AI ใช้ตัวไหน? ตรวจอะไร?

ใช้ Google Cloud Vision API (กู-เกิล คลาวด์ วิ-ชั่น) เฉพาะรูปที่ชั้น 1 บอกว่าน่าสงสัย

  1. ส่งไฟล์รูปไป Google
  2. ให้ตรวจหลายมุมพร้อมกัน เช่น ความปลอดภัยของภาพ, หาว่ารูปนี้มีบนเว็บไหม, อ่านป้าย/ข้อความในรูป, ติดป้ายประเภทวัตถุ
  3. ระบบแปลงผลเป็นคะแนนความเสี่ยง
  4. สูงมาก → ไม่ให้ลงขาย · กลาง → ติดธงรอตรวจ · ต่ำ → ผ่าน
ตัวอย่างที่เสี่ยง

รูปไปโผล่บนเว็บอื่นเยอะ (เหมือนรูปก็อปจากเน็ต)

ตัวอย่างที่เสี่ยง

ติดป้าย screenshot / สกรีนช็อต

ตัวอย่างที่เสี่ยง

เนื้อหาไม่เหมาะสม หรือไม่เข้ากับชื่อสินค้า

หน้า 6 — ทำไมเลือกตัวนี้

ทำไมต้องเป็น Google Cloud Vision?
AI มีเยอะทำไมถึงเลือกตัวนี้

เพราะงานนี้ไม่ใช่แค่ให้ AI คุย หรือ เดาความหมายข้อความ แต่ต้อง วิเคราะห์รูปภาพโดยตรง และมีฟีเจอร์ที่ระบบใช้จริงหลายอย่างในคำขอเดียว

1) หาว่ารูปมีบนเน็ตไหม

Web Detection — สำคัญมาก เพราะคนโกงชอบเอาภาพจาก Shopee / Lazada / เว็บอื่นมาลง

2) อ่านข้อความในรูป

OCR / Text Detection — ใช้ตอนแปะสกรีนช็อตเลขบัญชีในแชท

3) ติดป้ายประเภทภาพ

Label Detection — เช่น จับว่าเป็น screenshot / หน้าจอมือถือ

4) ตรวจเนื้อหาไม่เหมาะสม

Safe Search — กันรูปที่ไม่ควรขึ้นตลาด

ไม่ได้เลือกเพราะชื่อดัง แต่เลือกเพราะ ตรงกับปัญหาของระบบ: รูปหลอกลวง / รูปก็อปจากเน็ต / รูปที่มีข้อความเลี่ยงระบบ
ทำไมไม่ใช้ GPT / Gemini วิเคราะห์รูปอย่างเดียว?
วิเคราะห์ความหมายภาพได้บ้าง แต่สิ่งที่ต้องการหลักคือตรวจภาพซ้ำบนเว็บ และ OCR ที่เสถียร ซึ่งเป็นจุดแข็งของ Vision โดยเฉพาะ Web Detection

หน้า 6 — ความถูกต้องของ AI

แล้วจะรู้ได้ไงว่า AI ไม่พลาด?

ตอบตรงๆ: ไม่มีระบบไหนการันตีว่าไม่พลาด 100% เลยออกแบบเป็นหลายชั้น + เอียงไปทางปลอดภัย

  1. ชั้น 1 จับรูปไม่มีต้นทางกล้องก่อน — ลดภาระ AI และกันเคสก็อปชัดๆ บางส่วน
  2. ชั้น 2 ใช้หลายสัญญาณพร้อมกัน ไม่เชื่อแค่ตัวเดียว
  3. ผลรวมเอียงไปทางเข้มงวด: ถ้าเสี่ยงสูงจะไม่ปล่อยขึ้นตลาดทันที
  4. ถ้าระดับกลางจะ ติดธง ให้เจ้าหน้าที่ช่วยดูต่อได้ ไม่ปล่อย AI ตัดสินคนเดียวทุกเคส
  5. ถ้า Vision ล้มเหลวชั่วคราว ระบบไม่ปล่อยผ่านเงียบๆ — จะติดธงว่าตรวจเพิ่มไม่สำเร็จ
ทำไมไม่ใช้ AI ทุกรูป?
แพงและช้า รูปที่ดูเหมือนถ่ายจากมือถือจริง (มี EXIF ครบ) ชั้น 1 ผ่านได้เลย
เป้าหมายไม่ใช่ “AI แม่นเสมอ” แต่คือ ลดความเสี่ยงรูปหลอกลวงหลุดขึ้นตลาด ด้วยการกรองซ้อนกัน

หัวใจของระบบ

ชำระเงินเข้า Escrow (เอส-โครว)

ผู้ซื้อจ่ายเข้า “ระบบกลาง” ไม่โอนตรงเข้าบัญชีผู้ขาย

พอจ่ายสำเร็จ ผู้ขายเห็นว่ามีเงินเข้าแล้ว
แต่ยัง ถอนเข้าธนาคารไม่ได้ เพราะเงินยังอยู่ในบัญชีพักกลาง
ผู้ซื้อจ่าย→ พักกลาง→ ผู้ขายส่งของ→ ผู้ซื้อยืนยัน→ เงินพร้อมถอน

หน้าชำระเงิน

ผู้ซื้อจ่ายเงินยังไง?

หลังกดซื้อ จะเข้าหน้าชำระเงินของออเดอร์นั้น ผู้ซื้อเลือกได้ 2 ทางหลัก

ทางที่ 1: จ่ายออนไลน์

เช่น สแกน QR / จ่ายบัตร ผ่านระบบชำระเงิน → พอสำเร็จ ระบบยืนยันยอดเอง แล้วเงินเข้าพักกลาง

ทางที่ 2: โอนแล้วอัปโหลดสลิป

ผู้ซื้อโอนเงินเอง แล้วส่งรูปสลิปเข้ามา → ระบบต้องตรวจว่าสลิปนี้จริงและยอดตรงไหม

จุดสำคัญของทางที่ 2 คือต้องมีตัวช่วยอ่านสลิปอัตโนมัติ
ระบบใช้ EasySlip API (อี-ซี่-สลิป)

ตรวจสลิปอัตโนมัติ

EasySlip ทำงานยังไง?

EasySlip (อี-ซี่-สลิป) คือบริการภายนอกที่อ่านสลิปโอนเงินไทย แล้วส่งข้อมูลยอดเงินกลับมาให้ระบบเรา

  1. ผู้ซื้ออัปโหลดรูปสลิป
  2. ระบบกันใช้สลิปซ้ำก่อน (เทียบลายนิ้วมือไฟล์)
  3. ส่งไฟล์สลิปไปที่ EasySlip API
  4. EasySlip อ่านสลิป แล้วคืนค่ายอดเงินที่โอน
  5. ระบบเทียบยอดกับราคาสินค้าในออเดอร์
  6. ถ้ายอดตรง → ยืนยันชำระเงินสำเร็จ เงินเข้าพักกลาง
  7. ถ้ายอดไม่ตรง / อ่านไม่ได้ → ไม่ผ่านอัตโนมัติ ต้องแก้หรือรอตรวจเพิ่ม

ทำไมต้อง EasySlip

ทำไมไม่ให้แอดมินดูสลิปเองทุกใบ?

เร็ว

ผู้ซื้อรู้ผลเกือบทันที ไม่ต้องรอคนมานั่งเปิดสลิปทีละใบ

กันพลาดเรื่องยอด

เทียบยอดตัวเลขจากสลิปกับราคาสินค้าอัตโนมัติ

กันสลิปปลอม/ใช้ซ้ำ

ก่อนส่ง EasySlip ระบบกันใช้ไฟล์สลิปซ้ำข้ามออเดอร์อยู่แล้ว

ถ้า EasySlip อ่านสลิปไม่ได้ทำยังไง?
ระบบไม่ฟันธงว่าจ่ายสำเร็จเอง — จะพักสถานะไว้ให้ตรวจต่อแบบแมนนวล ไม่ปล่อยเงินเข้าขั้นถัดไปมั่วๆ
จ่ายผ่านแล้วผู้ขายถอนได้เลยไหม?
ยังไม่ได้ — เงินเข้าแค่บัญชีพักกลาง ต้องรอผู้ซื้อกดยืนยันรับของก่อน

คำสั่งซื้อ

ติดตามสถานะ + ยืนยันรับของ

รอชำระ→ ชำระแล้ว→ ส่งของแล้ว→ สำเร็จ

เมื่อกดยืนยันรับของ

  1. ตรวจว่าเป็นผู้ซื้อตัวจริง
  2. ตรวจว่าสถานะถึงขั้นที่กดได้
  3. เปลี่ยนเป็นสำเร็จ
  4. ย้ายเงิน พักกลาง → พร้อมถอน
กันปล่อยเงินซ้ำยังไง?
แต่ละออเดอร์มีรหัสอ้างอิงการปล่อยเงิน ถ้าเคยปล่อยแล้วจะไม่ปล่อยซ้ำ

หน้า 9 — จุดเสี่ยงสำคัญ

ระบบแชท + ตัวจับข้อความ

ถ้าคู่สัญญาชวนโอนนอกระบบ ความปลอดภัยของ Escrow จะหายไปทันที

เลยตรวจข้อความ ก่อนส่ง
ไม่ใช่ส่งก่อนแล้วค่อยมาไล่ลบทีหลัง

เดโมสดแนะนำ: เปิดแชทจริง แล้วพิมพ์ “โอนเข้าบัญชีผมเลย”

หน้า 9 — ชั้นที่ 1 กฎคืออะไร

“กฎที่เรากำหนดเอง” คือคำสั่งอะไร?

ไม่ใช่คำสั่งคุยกับ AI แต่เป็น เงื่อนไขในโปรแกรม แบบ “ถ้าเจอแบบนี้ แล้วทำแบบนั้น”

คลังคำ (Keyword)

เรามีลิสต์คำเสี่ยงไว้ล่วงหน้า
คำสั่งประมาณว่า:
ถ้าข้อความมีคำว่า “โอนเข้าบัญชี” → ให้คะแนน 65

รูปแบบ (Pattern)

เรากำหนดรูปแบบตัวเลข/ลิงก์ไว้
คำสั่งประมาณว่า:
ถ้าเจอเลขติดกัน 10–12 ตัว → น่าจะเป็นเลขบัญชี → ให้คะแนน 70

คำผสม

ตรวจมากกว่า 1 สิ่งพร้อมกัน
คำสั่งประมาณว่า:
ถ้ามี “ลดราคา” และมี “โอนตรง” → ให้คะแนน 72

เกณฑ์ตัดสิน

หลังได้คะแนนแล้ว
ถ้า ≥70 บล็อก · 45–69 ติดธง · ต่ำกว่านั้นผ่าน

พูดง่ายๆ: ชั้น 1 = ชุดคำสั่ง if/then ที่เขียนตายตัวไว้ล่วงหน้า
ไม่ได้นั่งอ่านความหมายเอง แต่เทียบตามกฎที่เราวางไว้

หน้า 9 — ชั้นที่ 1 ทำงานทีละขั้น

กฎพวกนี้ทำงานยังไงเมื่อมีคนพิมพ์?

  1. ผู้ใช้กดส่ง เช่น “โอนเข้าบัญชีผมเลย 4381234567”
  2. โปรแกรมเทียบกับคลังคำทีละคำ — เจอ “โอนเข้าบัญชี” → ได้ประมาณ 65
  3. เทียบกับรูปแบบตัวเลข — เจอเลขยาวคล้ายบัญชี → ได้ประมาณ 70
  4. เจอหลายสัญญาณ → บวกคะแนนเพิ่ม
  5. เอาคะแนนสุดท้ายไปเทียบเกณฑ์ → ถึงเกณฑ์บล็อกก็ไม่ให้ส่ง
คลังคำมาจากไหน?
เรารวบรวมคำที่คนมักใช้ชวนโอนนอกระบบไว้เอง เช่น โอนมาเลย, แอดไลน์, ไม่ผ่านแอป, พร้อมเพย์
ต่างจาก AI ยังไง?
กฎ = ต้องตรงตามที่เขียนไว้ถึงจะเจอ · AI = อ่านความหมายได้แม้พูดคนละคำ แต่ช้าและแพงกว่า

หน้า 9 — คะแนนความเสี่ยง

คะแนนมาจากไหน แล้วเอาไปใช้อย่างไร?

กฎเจอสิ่งนี้คะแนนผลโดยประมาณ
คำธนาคาร / ลิงก์ / เบอร์~45–55ติดธง หรือใกล้ๆ
คำชวนโอนนอกระบบ~65ติดธง / ใกล้บล็อก
เลขบัญชี หรือ ลดราคา+โอนตรง~70–72บล็อก
< 45 ผ่าน

ส่งได้ปกติ

45–69 ติดธง

ส่งได้ แต่เก็บประวัติให้ตรวจ

≥ 70 บล็อก

ไม่ให้ส่ง

“โอนเข้าบัญชีผมเลย 4381234567”
คำเสี่ยง + เลขบัญชี → คะแนนพุ่ง → บล็อก

หน้า 9 — ชั้นที่ 2

แล้ว AI เข้ามาตอนไหน? ทำไมต้องมี?

ชั้นที่ 1 เป็นกฎตายตัว จับได้ดีเมื่อข้อความตรงคำในคลังหรือตรงรูปแบบ แต่คนโกงมักพูดอ้อมๆ ไม่พิมพ์คำตรงๆ

กฎจับได้ชัด

“โอนเข้าบัญชีผมเลย” → ตรงคลังคำ → ได้คะแนนความเสี่ยงสูง

กฎอาจพลาด

“ส่งเงินมาที่นี้เลยนะ ไม่ง้อแอป” → ไม่ตรงคำในลิสต์ แต่ความหมายเหมือนกัน

เลยต้องมีชั้น 2 เป็น โมเดลภาษา มาอ่านความหมาย
ตัวหลักที่ใช้คือ Groq API (กร็อก) โมเดล Llama 3.3 70B (ลา-มา)

หน้า 9 — ใช้ AI ตัวไหน

เรียก API ตัวไหน? ทำไมต้องตัวนี้?

ระบบเรียกโมเดลภาษาแบบมีลำดับสำรอง ถ้าตัวแรกใช้ไม่ได้จะลองตัวถัดไป

  1. ตัวหลัก: Groq (กร็อก) + โมเดล Llama 3.3 70B
  2. ตัวสำรอง 1: OpenRouter (โอ-เพิน-ราว-เตอร์)
  3. ตัวสำรอง 2: Gemini (เจ-มิ-ไน) ของ Google

ทำไมเลือก Groq เป็นตัวหลัก?

เร็ว

แชทต้องตอบเกือบทันที ถ้ารอ AI นาน ผู้ใช้รู้สึกว่าระบบค้าง Groq เน้นความเร็วสูง

เหมาะกับงานจัดประเภท

งานนี้ไม่ใช่ให้ AI แต่งนิทาน แต่ให้ตัดสินสั้นๆ ว่า ผ่าน / ติดธง / บล็อก

ต้นทุนคุ้ม

ข้อความแชทมีจำนวนมาก ต้องเลือกตัวที่เรียกบ่อยได้โดยไม่แพงเกิน

อ่านภาษาพูดได้

ช่วยจับประโยคอ้อมๆ / สแลงไทย ที่ไม่มีในคลังคำชั้น 1

สรุป: เลือกเพราะ เร็ว + เหมาะกับงานตัดสินข้อความ + มีตัวสำรองถ้าล่ม ไม่ได้เลือกเพราะชื่อดังอย่างเดียว

หน้า 9 — เงื่อนไขเรียก AI

ต้องแบบไหนถึงดึง API ของ AI?

ไม่เรียก Groq ทุกข้อความ มีเกณฑ์ก่อนส่ง เพื่อไม่เสียเวลาและค่าใช้จ่าย

  1. ข้อความถูกตรวจด้วยกฎชั้น 1 ก่อนเสมอ
  2. ถ้าคะแนนความเสี่ยงประมาณ 25–79 → ส่งต่อให้ Groq อ่านเพิ่ม
  3. ถ้าคะแนนต่ำมาก (ปลอดภัยชัด) → ไม่เรียก AI
  4. ถ้าคะแนนสูงมาก (≥80 เช่น มีเลขบัญชีชัด) → ตัดสินด้วยกฎเลย ไม่เสียค่า AI
  5. หรือมีตัวเลขยาวๆ น่าสงสัย แต่ชั้น 1 ยังไม่ฟันธง → ก็ส่ง AI ช่วยดู
ทำไมไม่ส่งทุกข้อความเข้า Groq?
ช้า แพง และของที่ชัดๆ กฎจับได้ดีกว่าอยู่แล้ว — AI เก็บไว้ใช้กับเคสกำกวม
ถ้า Groq ล่มทำยังไง?
ระบบสลับไป OpenRouter แล้วค่อย Gemini ตามลำดับ ถ้าทุกตัวใช้ไม่ได้ จะไม่ปล่อยผ่านเงียบๆ ในเคสที่น่าสงสัย

หน้า 9 — หลักการทำงานของ AI

เมื่อเรียก Groq แล้วทำอะไรต่อ?

  1. ระบบประกอบคำสั่งส่งให้โมเดล: ข้อความต้นฉบับ + สิ่งที่ชั้น 1 เจอแล้ว
  2. บอกโมเดลให้ตอบแบบโครงสร้างชัดเจน: ผ่าน / ติดธง / บล็อก พร้อมเหตุผลสั้นๆ
  3. เน้นให้จับภาษาพูดอ้อม เช่น “โอนมาเลย”, “คุยนอกแอพ”, “ลดให้ถ้าไม่ผ่านระบบ”
  4. ระบบรวมผลชั้น 1 กับผล AI โดยยึดฝั่งที่เข้มงวดกว่า
  5. ตัวอย่าง: ชั้น 1 บอก “ผ่าน” แต่ Groq บอก “บล็อก” → สรุปเป็นบล็อก
ทำไมต้องยึดฝั่งเข้มงวดกว่า?
เป้าหมายคือกันเลี่ยงพักเงินกลาง ถ้ามีฝั่งใดเห็นความเสี่ยง ให้เอียงไปทางปลอดภัยก่อน
ทำไมต้องมี AI ทั้งที่มีกฎอยู่แล้ว?
กฎเก่งเรื่องคำตรงๆ AI เก่งเรื่องภาษาพูดอ้อม ความหมายแฝง และคำใหม่ที่ยังไม่ได้อยู่ในคลัง

หน้า 9 — สรุป 2 ชั้น

ชั้น 2 = Groq

ถูกเรียกเฉพาะเคสกลางๆ ที่พูดอ้อมๆ อ่านความหมายแล้วช่วยตัดสิน

ผลรวม

ของชัดจบที่กฎ ของกำกวมค่อยเสียค่า AI

หลังออเดอร์สำเร็จ

  • รีวิวซ้ำออเดอร์เดิมไม่ได้
  • คะแนนไปรวมเป็นความน่าเชื่อถือผู้ขาย
ทำไมต้องรอให้สำเร็จก่อน?

หน้ารีวิวจริงจะเปิดจากปุ่มหลังออเดอร์สำเร็จ (write_review.php)
