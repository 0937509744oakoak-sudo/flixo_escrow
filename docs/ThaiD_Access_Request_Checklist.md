# เช็คลิสต์ยื่นขอใช้บริการ ThaiD / DOPA-Digital ID สำหรับ FLIXO

เอกสารนี้รวบรวมสิ่งที่ต้องเตรียมเพื่อยื่นขอสิทธิ์เชื่อมต่อระบบพิสูจน์และยืนยันตัวตน
ทางดิจิทัลของกรมการปกครอง โดยส่วนที่เป็นข้อมูลทางเทคนิค (ภาคผนวก ก) ดึงมาจากโค้ด
ที่พัฒนาไว้แล้วในโปรเจกต์ จึงนำไปกรอกแบบคำขอได้โดยตรง

อ้างอิงหลักเกณฑ์: ประกาศกรมการปกครอง เรื่อง หลักเกณฑ์การอนุญาตให้หน่วยงานของรัฐ
และหน่วยงานเอกชนใช้บริการระบบพิสูจน์และยืนยันตัวตนทางดิจิทัล (DOPA-Digital ID)
ประกาศในราชกิจจานุเบกษา 13 กรกฎาคม 2566

---

## 1. ขั้นตอนตามประกาศกรมการปกครอง

| ขั้น | สิ่งที่ต้องทำ | หมายเหตุ |
|---|---|---|
| 1 | ดาวน์โหลดประกาศ ตัวอย่างหนังสือ และแบบการขออนุญาต | จาก [หน้าประกาศของสำนักบริหารการทะเบียน](https://www.bora.dopa.go.th/information/activity-news/35807/) |
| 2 | ทำหนังสือขออนุญาตใช้งาน เรียน อธิบดีกรมการปกครอง | ส่งไปรษณีย์ถึง สำนักบริหารการทะเบียน 59 หมู่ 11 ต.บึงทองหลาง อ.ลำลูกกา จ.ปทุมธานี 12150 |
| 3 | ลงทะเบียนที่ https://digitalid.bora.dopa.go.th | ทำพร้อมกับข้อ 2 ได้ ไม่ต้องรอ |
| 4 | รอกรมฯ อนุมัติในระบบลงทะเบียน | จะได้รับหนังสืออนุญาต + คู่มือการพัฒนาระบบ + credential |

เงื่อนไขที่ประกาศระบุไว้และควรรับทราบก่อนยื่น

- หน่วยงานต้องจัดหาอุปกรณ์และรับผิดชอบค่าใช้จ่ายที่เกิดขึ้นเองทั้งหมด
- ใช้ประโยชน์ได้ตามวัตถุประสงค์ที่ได้รับอนุญาตเท่านั้น
- กรมการปกครองสงวนสิทธิ์ในการอนุญาต

## 2. เรื่องที่ต้องตัดสินใจก่อนยื่น

สามข้อนี้กรอกในแบบคำขอไม่ได้ถ้ายังไม่ตัดสินใจ และเป็นจุดที่ทำให้คำขอตกบ่อยที่สุด

### 2.1 ผู้ยื่นคือใคร

ประกาศเขียนถึง "หน่วยงานของรัฐ" และ "หน่วยงานเอกชน" ไม่ได้เปิดให้บุคคลธรรมดายื่น
ในนามตัวเอง แนวทางที่เหมาะกับ FLIXO ที่สุดคือ **ยื่นในนามคณะ/มหาวิทยาลัย**
เพราะโครงการได้รับการรับรองจากสถาบันอยู่แล้ว

โครงการ "ระบบเอสโครว์อัจฉริยะและแพลตฟอร์มตรวจจับการทุจริตด้วยเอไอสำหรับการซื้อขาย
ออนไลน์ระหว่างบุคคล" ได้รับทุนอุดหนุนการพัฒนาผลิตภัณฑ์ต้นแบบของนักศึกษา
งบประมาณรายได้ประจำปี 2569 จำนวน 10,000 บาท

- ผู้ดำเนินโครงการ: นางสาวณภัทร แซ่ตั้ง, นางสาวอริษรา ราชนิยม, นายธนพัตร ฉุยสุริฉาย
- อาจารย์ที่ปรึกษา 6 ท่าน รวมหัวหน้าสาขาวิศวกรรมคอมพิวเตอร์ (ผศ.ดร.ขวัญเรือน รัศมี)
  และหัวหน้าสาขาวิศวกรรมหุ่นยนต์ (ผศ.ดร.เศรษฐกาล โปร่งนุช)

**ผู้ลงนามในหนังสือ** ควรเป็นระดับคณบดีหรืออธิการบดี เนื่องจากเป็นหนังสือระหว่างหน่วยงาน
หัวหน้าสาขาโดยทั่วไปไม่มีอำนาจลงนามผูกพันสถาบันกับหน่วยงานภายนอก แนวทางปฏิบัติคือ
ให้อาจารย์ที่ปรึกษาเสนอเรื่องผ่านสาขาและคณะขึ้นไปตามลำดับ

ทางเลือกสำรองหากยื่นในนามสถาบันไม่สำเร็จ

1. ยื่นในนามนิติบุคคล ถ้ามีการจดทะเบียนบริษัทแล้ว
2. ขอผ่านผู้ให้บริการตัวกลางที่เชื่อม DOPA ไว้แล้ว (เร็วกว่าแต่มีค่าใช้จ่ายและยังต้องมีนิติบุคคล)

### 2.2 โดเมนและ Callback URL

ต้องเป็น HTTPS และต้องตรงกับที่จดไว้ทุกตัวอักษร `http://localhost` ใช้ไม่ได้
ตอนนี้ `BASE_URL` ในเครื่องยังเป็น `http://localhost/flixo_escrow` จึงต้องเตรียมอย่างใดอย่างหนึ่ง

- Named tunnel (cloudflared) ที่ได้โดเมนคงที่ — เหมาะกับช่วงพัฒนา
- Deploy ขึ้น Railway / Render ที่มี HTTPS ให้อยู่แล้ว — เหมาะกับ production

**ห้ามใช้ tunnel แบบสุ่ม URL ใหม่ทุกครั้งที่เปิด** เพราะจะไม่ตรงกับ redirect URI ที่จดไว้

### 2.3 IP ของเซิร์ฟเวอร์สำหรับ whitelist

กรมฯ ต้องการ IP ปลายทางล่วงหน้า ถ้า deploy บน PaaS ที่ IP ขาออกเปลี่ยนได้
ต้องเลือกแผนที่มี static outbound IP หรือวาง reverse proxy ที่ IP คงที่ไว้หน้าระบบ

### 2.4 ทบทวน scope ก่อนยื่น (ข้อเสนอแนะ)

ค่า default ในโค้ดตอนนี้คือ

```
openid pid name given_name family_name birthdate ial
```

`birthdate` **ยังไม่ถูกใช้ที่ใดในระบบ** การขอข้อมูลที่ไม่ได้ใช้ขัดกับหลัก data minimisation
ของ PDPA และมักถูกกรมฯ ตั้งคำถาม แนะนำให้ตัดออกเหลือ

```
openid pid name given_name family_name ial
```

ถ้าอนาคตจะบังคับอายุขั้นต่ำ 18 ปี ค่อยยื่นขอเพิ่มพร้อมเหตุผล

## 3. เอกสารที่ต้องเตรียม

- [ ] หนังสือขออนุญาตใช้งาน เรียน อธิบดีกรมการปกครอง (ตามตัวอย่างของกรมฯ)
      — ออกในนามคณะ/มหาวิทยาลัย มีเลขที่หนังสือ วันที่ และลายมือชื่อผู้มีอำนาจ
- [ ] แบบการขออนุญาตใช้บริการระบบ DOPA-Digital ID (ตามแบบของกรมฯ)
- [ ] หนังสือรับรองจากหน่วยงานต้นสังกัด
- [ ] สำเนาบัตรประชาชนผู้มีอำนาจลงนาม
- [ ] เอกสารอธิบายระบบและวัตถุประสงค์การใช้งาน (ใช้ภาคผนวก ก ด้านล่าง)
- [ ] นโยบายความเป็นส่วนตัว / แนวทางปฏิบัติตาม PDPA (ระบบมีหน้า `privacy_policy.php` อยู่แล้ว)

**เอกสารแนบสนับสนุน** (ไม่ใช่เอกสารบังคับ แต่ช่วยยืนยันว่าโครงการได้รับการรับรองจากสถาบัน)

- [ ] ประกาศผลการคัดเลือกทุนอุดหนุนการพัฒนาผลิตภัณฑ์ต้นแบบของนักศึกษา ประจำปี 2569

หมายเหตุ: ประกาศผลทุนเป็นเอกสารแสดงความยินดี ไม่มีหัวกระดาษ เลขที่หนังสือ หรือลายมือชื่อ
จึงใช้แทนหนังสือรับรองจากต้นสังกัดไม่ได้ ให้แนบเป็นหลักฐานประกอบเท่านั้น

## ภาคผนวก ก — ข้อมูลทางเทคนิคของระบบ FLIXO

ส่วนนี้ตอบคำถามที่แบบคำขอและคู่มือของกรมฯ มักถาม โดยอ้างอิงจากโค้ดที่พัฒนาไว้จริง

### ก.1 ข้อมูลระบบ

| หัวข้อ | ค่า |
|---|---|
| ชื่อระบบ | FLIXO — ระบบซื้อขายสินค้าออนไลน์แบบมีคนกลางถือเงิน (Escrow) |
| ลักษณะการใช้งาน | Web application (PHP 8.2 + MySQL/MariaDB) |
| บทบาทในระบบ ThaiD | Relying Party (RP) |
| มาตรฐานที่ใช้ | OpenID Connect 1.0 / OAuth 2.0 — Authorization Code Flow |
| Endpoint ที่เรียก | `/.well-known/openid-configuration`, `authorization`, `token`, `jwks`, `userinfo` |
| อัลกอริทึมตรวจลายเซ็น | ES256 (ตามที่ DOPA ประกาศใน discovery) |
| Redirect URI | `https://<โดเมนที่จดไว้>/controllers/ThaiDController.php` |

### ก.2 วัตถุประสงค์การใช้งาน

ระบบเป็นตัวกลางถือเงินระหว่างผู้ซื้อและผู้ขาย เงินจะถูกพักไว้จนกว่าธุรกรรมจะสำเร็จ
จึงต้องพิสูจน์ตัวตนผู้ใช้ก่อนอนุญาตให้ **ถอนเงินออกจากระบบ** และก่อน **เปิดร้านขายสินค้า**
เพื่อป้องกันการฉ้อโกงและการใช้บัญชีม้า

การพิสูจน์ตัวตนด้วย ThaiD ใช้แทนการให้ผู้ใช้อัปโหลดภาพบัตรประชาชนและภาพใบหน้า
ซึ่งลดปริมาณข้อมูลส่วนบุคคลที่ระบบต้องจัดเก็บลงอย่างมีนัยสำคัญ

ขอบเขตการใช้งาน: เป็นโครงการพัฒนาผลิตภัณฑ์ต้นแบบของนักศึกษาที่ได้รับทุนอุดหนุน
จากงบประมาณรายได้ของสถาบัน ประจำปีงบประมาณ 2569 มิใช่การให้บริการเชิงพาณิชย์

### ก.3 Scope ที่ขอใช้และเหตุผลรายตัว

| Scope | ใช้ทำอะไร | เก็บลงฐานข้อมูลหรือไม่ |
|---|---|---|
| `openid` | จำเป็นตามมาตรฐาน OIDC | ไม่ |
| `pid` | ทำ blind index กันผู้ใช้คนเดียวยืนยันหลายบัญชี | เก็บเฉพาะค่าแฮช ไม่เก็บเลขบัตร |
| `given_name`, `family_name` | ใช้จับคู่กับชื่อเจ้าของบัญชีธนาคารตอนถอนเงิน | เก็บใน `users.real_name` |
| `name` | ใช้แทนเมื่อไม่มี given/family | เก็บใน `users.real_name` |
| `ial` | ตัดสินว่าอนุมัติอัตโนมัติหรือส่งเจ้าหน้าที่ตรวจ | เก็บใน log การยืนยันตัวตน |

ระดับความน่าเชื่อถือขั้นต่ำที่ระบบยอมรับสำหรับการอนุมัติอัตโนมัติคือ **IAL 2.3**
(ยืนยันผ่านแอป ThaiD + ข้อมูลชิปบัตร) ต่ำกว่านี้จะเข้าคิวให้เจ้าหน้าที่ตรวจสอบ ไม่อนุมัติเอง

### ก.4 การจัดเก็บข้อมูลส่วนบุคคล

**เก็บ**

| ข้อมูล | ที่จัดเก็บ | รูปแบบ |
|---|---|---|
| ชื่อ-นามสกุล | `users.real_name` | ข้อความ |
| สถานะการยืนยัน | `users.is_verified`, `kyc_status`, `kyc_verified_at` | ค่าสถานะ |
| ตัวระบุจากเลขบัตร | `user_oauth_accounts.provider_user_id` | HMAC-SHA256 (blind index) |
| บันทึกการยืนยัน | `ekyc_sessions.raw_payload` | claims โดยเลขบัตรถูกปิดบัง |

**ไม่เก็บ**

- เลขประจำตัวประชาชนในรูปแบบที่อ่านได้ — เก็บเฉพาะค่าแฮชที่มีคีย์ลับกำกับ
  จึงย้อนกลับเป็นเลขบัตรไม่ได้ และในบันทึก log แสดงเฉพาะรูปแบบปิดบัง (`1********2345`)
- ที่อยู่ตามทะเบียนบ้าน — ไม่ขอ scope `address` / `house_address`
- access token และ refresh token — ใช้แล้วทิ้งทันทีภายในคำขอเดียว ไม่บันทึกลงฐานข้อมูล

### ก.5 มาตรการความปลอดภัย

| มาตรการ | รายละเอียด |
|---|---|
| การเข้ารหัสระหว่างส่ง | HTTPS บังคับทั้งระบบ (`FORCE_HTTPS=1`) |
| การเข้ารหัสที่จัดเก็บ | AES-256-GCM สำหรับข้อมูลส่วนบุคคล (เบอร์โทร เลขบัญชีธนาคาร ภาพเอกสาร) |
| ป้องกัน CSRF | โทเคน CSRF ทุกคำขอที่เปลี่ยนสถานะ |
| ป้องกัน replay | พารามิเตอร์ `state` และ `nonce` แบบใช้ครั้งเดียว หมดอายุใน 15 นาที |
| ตรวจสอบ id_token | ตรวจลายเซ็น ES256 กับ JWKS ของกรมฯ พร้อมตรวจ `iss`, `aud`, `exp`, `iat`, `nonce` |
| ป้องกัน session hijack | Cookie ตั้ง HttpOnly, Secure, SameSite=Lax |
| จำกัดอัตราการเรียก | จำกัดจำนวนครั้งการเข้าสู่ระบบและการรีเซ็ตรหัสผ่าน |
| บันทึกการเข้าถึงข้อมูล | ตาราง `pii_audit_logs` บันทึกทุกครั้งที่เจ้าหน้าที่เปิดดูข้อมูลส่วนบุคคล |
| ควบคุมสิทธิ์ | RBAC แยกสิทธิ์ `kyc.review` และ `pii.view` |

### ก.6 การขอความยินยอมตาม PDPA

ระบบบันทึกความยินยอมประเภท `kyc_data_collection` ลงตาราง `user_consents`
**ก่อน** พาผู้ใช้ออกจากเว็บไซต์ไปยังระบบของกรมการปกครอง โดยบันทึกเลข IP
User-Agent เวลา และเลขเวอร์ชันของนโยบายความเป็นส่วนตัวที่ผู้ใช้ยอมรับ

ผู้ใช้ถอนความยินยอมได้เองที่หน้า `privacy.php` และขอสำเนาข้อมูลของตนเอง
(data subject access request) ได้จากหน้าเดียวกัน

## ภาคผนวก ข — ค่าที่ต้องนำมาใส่หลังได้รับอนุมัติ

เมื่อกรมฯ ส่ง credential มาแล้ว ให้ใส่ค่าเหล่านี้ในไฟล์ `.env` ของระบบ

| สิ่งที่ได้รับจากกรมฯ | ตัวแปรในระบบ |
|---|---|
| Client ID | `THAID_CLIENT_ID` |
| Client Secret | `THAID_CLIENT_SECRET` |
| API Key | `THAID_API_KEY` |
| ชื่อ header ของ API Key (ดูในคู่มือ) | `THAID_API_KEY_HEADER` |
| Callback URL ที่จดไว้ | `THAID_REDIRECT_URI` |
| สภาพแวดล้อมที่ได้รับสิทธิ์ | `THAID_ISSUER` |

ค่า `THAID_ISSUER` — sandbox คือ `https://imauthsbx.bora.dopa.go.th`
production คือ `https://imauth.bora.dopa.go.th` (ค่า default ในโค้ดชี้ไป sandbox ไว้แล้ว)

นอกจากนี้ต้องตั้ง `ENCRYPTION_KEY` ความยาวอย่างน้อย 32 ตัวอักษร มิฉะนั้นระบบจะปฏิเสธ

### สิ่งที่ต้องตรวจสอบกับคู่มือของกรมฯ

สามข้อนี้พัฒนาไว้ตามมาตรฐาน OIDC แล้ว แต่ยังยืนยันกับระบบจริงไม่ได้จนกว่าจะมี credential

1. `pid` ส่งมาใน `id_token` โดยตรง หรือต้องเรียก userinfo เพิ่ม (โค้ดรองรับทั้งสองทาง)
2. ชื่อ header ที่ใช้ส่ง API Key — ค่า default ในโค้ดคือ `Consumer-Key`
3. รองรับ PKCE หรือไม่ — ถ้ารองรับให้ตั้ง `THAID_USE_PKCE=1`
