## สไลด์ 4 — สถาปัตยกรรมระบบ (บท 3)

**4 ชั้น**
```text
Browser (HTML/JS)
   ↓ HTTPS
PHP Controllers / Services (Apache)
   ↓
MySQL (+ Redis / Object Storage)
   ↓
External APIs: Google Auth · Omise · EasySlip
               AiGen/Sumsub · Vision · Groq/OpenRouter/Gemini
```

**จุดพูดสั้น**
- Login ≠ e-KYC  
- MySQL = source of truth ของเงิน  
- API ล้มแล้วไม่ปล่อยเงินโดยไม่มีเงื่อนไข  

**Visual:** ภาพที่ 3.2

## สไลด์ 5 — ข้อค้นพบหลักด้านแชท (Cascade Gap)

**หัวข้อ:** ทำไม cascade เดิมยังพลาด

**Insight**
- ข้อความ bait บางแบบได้คะแนน Regex = 0 → **ไม่เรียก LLM**  
- เกิดช่องว่าง cascade gap  

**ชุดข้อมูล**
| รายการ | ค่า |
|--------|-----|
| ภาพแคปแชท | 100 |
| ข้อความหลัง OCR (N) | **333** |
| ALLOW / BLOCK | 270 / 63 |

**คำตอบที่เสนอ:** Soft-trigger บังคับ escalate เมื่อเจอ cue อ่อน โดยยังไม่บล็อกจาก cue นั้นเพียงอย่างเดียว

---

## สไลด์ 6 — สถาปัตยกรรมคัดกรองแชท 3 ชั้น + Soft

```text
Message
 → Tier 1 Regex/Heuristics + soft cues
      ├─ ชัดเจน → ALLOW/BLOCK
      └─ mid / soft-trigger → Tier 2 LLM (Groq→OpenRouter→Gemini)
                                ├─ OK → merge
                                └─ fail → Tier 3 Fallback
```

**จุดขาย:** ไม่ใช่แค่ “มี LLM” แต่คือ **เมื่อไหร่ควรเรียก LLM**

## สไลด์ 7 — ผล Live Ablation (ตัวเลขหลัก) ⭐

**หัวข้อ:** N=333 · โหมด live · 3 ระบบ

| ระบบ | Acc | Prec | Rec | F1 | FN | FP | Tier1 |
|------|-----|------|-----|----|----|----|-------|
| Regex-only | 94.3% | 0.978 | 0.714 | 0.826 | 18 | 1 | — |
| Cascade (ไม่มี soft) | 90.7% | 0.758 | 0.746 | 0.752 | 16 | 15 | 77.5% |
| **Cascade+Soft** | **93.4%** | 0.759 | **0.952** | **0.845** | **3** | 19 | **70.6%** |

**Effect size ที่ต้องพูด**
- Recall: 0.746 → **0.952**  
- FN: 16 → **3** (กู้จาก cascade ได้ **13** เคส)  
- ยังจบที่ Tier1 **70.6%** → ประหยัดการเรียก LLM  

**ห้ามเคลม**
- Acc ชนะ regex (94.3 vs 93.4, McNemar p≈0.73)  
- McNemar cascade→soft p≈0.081 ยังไม่ <0.05 → เน้นขนาดผล FN/Recall

## สไลด์ 8 — ผลอื่นในขอบเขตที่พิสูจน์ได้

**Escrow / ระบบ**
- กักเก็บ · ระงับ · ปล่อย/คืน ตามสถานะได้  
- Fallback จำลอง 10/10 สำเร็จ  
- UAT ฟังก์ชัน 12/12 ผ่าน  

**e-KYC (พูดระวัง)**
- ท่อจำลอง: ตรวจแมปสถานะได้  
- ภาพจริง: **4 คู่** แยกคลาสได้ที่เกณฑ์ 80  
- **อย่าขึ้นสไลด์ว่า 100% ใหญ่ ๆ**  
  เขียนแทน: *Real-image test: 4 pairs, separated at threshold 80*

**แบบประเมินผู้ใช้**
- N=**33** · Likert 1–5  
- ค่าเฉลี่ยรวม **4.20** · พึงพอใจโดยรวม **4.30**  
- จุดงงบ่อย: การกักเงิน / e-KYC

## สไลด์ 9 — สิ่งที่ยังไม่พิสูจน์ (ตารางข้ออ้าง)

| ข้ออ้าง | สถานะ |
|---------|--------|
| เกณฑ์ 80 เหมาะสมกับประชากร | ยังไม่พิสูจน์ |

**ประโยคปิด**
> การมีระบบครบสี่ขอบเขต ≠ ทุกขอบเขตถูกพิสูจน์แล้วว่าทำงานดี

## สไลด์ 10 — สรุปและข้อเสนอแนะ

**สรุป**
1. ได้ต้นแบบเชื่อม Escrow + e-KYC + AI คัดกรอง + Dispute (คนตัดสินเงิน)  
2. Soft-trigger ปิด cascade gap บนชุด N=333: Rec 0.952, FN=3, Tier1 70.6%  
3. ผู้ใช้ทดลอง N=33 ให้คะแนนเฉลี่ยรวม 4.20/5  

**ข้อเสนอแนะสั้น**

- วัดรอบก่อน–หลังของแอดมินกับ dispute AI  
- ขยายกลุ่มผู้ใช้ / ทดลองภาคสนามจำกัด  

**Closing**
> Prototype ที่พิสูจน์กลไกหลักและขอบเขตหลักฐานได้ชัด ไม่โม้ผลเกินชุดทดสอบ

## สไลด์ 11 — Q&A เตรียมตอบ

| คำถาม | คำตอบสั้น |
|--------|-----------|
| ทำไม Threshold 80? | ในชุด 4 คู่ อยู่ระหว่างคะแนนเจ้าของจริงกับคนละคน ยังไม่ใช่จุดเหมาะสมประชากร |
| e-KYC กันถือรูปได้ไหม? | โหมดหลักเป็นภาพนิ่ง ยังไม่ทดสอบ presentation attack |
| Soft-trigger คืออะไร? | สัญญาณอ่อนที่บังคับเรียก LLM แม้คะแนน regex = 0 |
| ทำไม Acc ไม่ชนะ regex? | จุดขายคือ recall recovery + ประหยัด API ไม่ใช่ชนะ accuracy |
| เงินอยู่ที่ไหน? | สถานะ hold/release บันทึกใน MySQL เป็น source of truth; ชำระผ่าน Omise/สลิป |
| AI ตัดสินข้อพิพาทเองไหม? | ไม่ — AI แนะนำ แอดมินเป็นคนกดเงิน |
| แบบประเมิน N=33 พอไหม? | พอสำหรับกลุ่มทดลองใช้ ไม่แทนตลาดจริง |
